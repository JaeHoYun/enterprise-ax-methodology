# 06. 실행 환경 선택

> **요약.** 어디서 돌릴 것인가는 과제마다 내리는 판단이고, 어느 한쪽이 기본값이 아닙니다. 선택지는 외부 사업자의 서비스를 쓰는 퍼블릭, 사내에서 운영하는 온프렘, 둘을 나눠 쓰는 혼합입니다. 판단 축은 데이터 민감도와 규제, 사용량과 단가, 지연과 가용성, 결정의 되돌림 가능성, 운영 역량의 다섯 가지입니다. 환경을 옮길지는 선언이 아니라 신호를 보고 과제 단위로 정합니다. 이미 외부에서 돌리는 것을 사내로 되돌리는 일도 전면 철수가 아니라 선별적인 재배치로 나타납니다.

---

## 6.1 세 가지 선택지

- **퍼블릭.** 외부 사업자가 제공하는 AI 서비스와 클라우드 자원을 빌려 씁니다. 쓴 만큼 비용을 냅니다.
- **온프렘.** 사내 또는 자사가 통제하는 시설의 장비에서 운영합니다. 데이터가 조직의 경계를 벗어나지 않은 채 사내에서 운영하는 AI를 흔히 Private AI라고 부릅니다.
- **혼합.** 과제나 작업의 성격에 따라 둘을 나눠 씁니다.

| 선택지 | 유리한 조건 | 불리한 조건 |
|--------|-------------|-------------|
| 퍼블릭 | 빠르게 시작해야 함. 사용량이 적거나 들쭉날쭉함. 최신 모델이 필요함. 운영 인력이 없음 | 민감한 데이터를 밖으로 보낼 수 없음. 사용량이 커지면 비용이 빠르게 늚. 응답 지연과 장애를 스스로 통제하기 어려움. 특정 사업자에 묶일 수 있음 |
| 온프렘 | 데이터를 밖으로 보낼 수 없음. 사용량이 많고 꾸준함. 지연과 가용성을 직접 통제해야 함 | 초기 투자와 장비 조달 기간이 큼. 운영 인력이 필요함. 사용률이 낮으면 단위 비용이 높음. 최신 모델의 반영이 늦을 수 있음 |
| 혼합 | 과제마다 데이터 민감도와 사용 양상이 다름. 여러 과제를 가진 조직에서 흔함 | 두 환경을 함께 운영하는 복잡성. 데이터와 권한의 기준을 양쪽에 일관되게 적용해야 함 |

## 6.2 다섯 가지 판단 축

- **데이터 민감도와 규제.** 과제에 들어가는 데이터가 조직 밖으로 나가도 되는지를 먼저 봅니다. 개인정보, 영업비밀, 업종별 규제가 걸린 데이터라면 선택지가 좁아집니다. 다만 규제는 바뀝니다. 한국의 관련 일정과 최근의 완화 흐름은 [부록 A2](../appendix/A2-kr-regulatory-timeline.md)에 정리했습니다. 규제 때문에 무조건 사내여야 한다는 전제는 주기적으로 다시 확인할 필요가 있습니다.
- **사용량과 단가.** 쓴 만큼 내는 방식은 사용량이 적을 때 유리하고, 사용량이 많고 꾸준해지면 사내 운영의 단위 비용이 낮아지는 구간이 옵니다. 반대로 사내 장비는 사용률이 낮으면 단위 비용이 높습니다. 어느 쪽이 유리한지는 자사의 사용량과 견적으로 계산해야 하며, 일반적인 기준선에 기대지 않습니다.
- **지연과 가용성.** 지연은 응답이 늦어지는 정도이고 가용성은 서비스가 멈추지 않고 돌아가는 정도입니다. AI가 업무에 깊이 결합될수록 응답 속도와 장애 대응을 직접 통제할 필요가 커집니다. 보조 도구라면 외부 서비스의 장애를 감수할 수 있지만, 업무가 멈추는 자리라면 사정이 다릅니다.
- **결정의 되돌림 가능성.** 외부 서비스로 시작하는 것은 되돌리기 쉬운 결정이고, 장비를 사서 환경을 짓는 것은 되돌리기 어려운 결정입니다. [04장 4.5절](04-validation.md)의 구분을 그대로 적용해, 되돌리기 어려운 쪽은 증거가 쌓인 뒤에 정합니다. 반대 방향의 위험도 있습니다. 특정 사업자의 고유 기능에 깊이 기대면 외부 서비스도 되돌리기 어려워집니다.
- **운영 역량.** 사내 환경은 지은 뒤가 시작입니다. 장비, 소프트웨어, 보안, 모델의 갱신을 맡을 사람이 있는지를 봅니다. 운영을 외부에 맡긴 사내 환경은 [05장 5.3.5절](05-solve-path.md)과 같은 문제를 겪습니다.

## 6.3 출발점

모든 과제를 같은 환경에서 시작할 필요는 없습니다.

| 조건 | 알맞은 출발점 |
|------|---------------|
| 민감한 데이터가 없고 빠른 확인이 목적 | 외부 서비스로 빠르게 검증 |
| 민감한 데이터가 일부 있고 되돌릴 수 있는 실험 | 익명화하거나 합성한 데이터로 외부에서 검증 |
| 규제나 기밀 때문에 외부 전송이 불가능 | 처음부터 사내 환경에서 검증. [04장 4.8절](04-validation.md)의 유의점 참고 |
| 검증을 마쳤고 실제 데이터로 실제 규모의 운영이 필요 | 6.2절의 다섯 축으로 과제별 판단 |

외부에서 검증하더라도 평가 데이터셋과 데이터 처리 경로는 다시 쓸 수 있는 형태로 남깁니다. 환경을 옮길 때 처음부터 다시 시작하지 않기 위해서입니다.

## 6.4 환경을 옮기는 신호

환경의 재검토는 선언이 아니라 신호에서 시작합니다.

**퍼블릭에서 온프렘으로 옮기는 것을 검토할 신호.**

- 과제가 실제 데이터와 민감한 정보를 요구하기 시작합니다.
- 사용량이 늘어 외부 서비스의 누적 비용이 사내 운영 비용의 견적을 넘습니다.
- 규제나 감사의 요구가 외부 전송을 막습니다.
- 업무와의 결합이 깊어져 지연과 장애를 직접 통제해야 합니다.

**온프렘에 두지 않거나 퍼블릭으로 돌리는 것을 검토할 신호.**

- 사내 장비의 사용률이 계속 낮습니다.
- 운영 인력을 확보하거나 유지하지 못합니다.
- 필요한 모델이나 기능이 사내 환경에서 제공되지 않습니다.
- 규제가 완화되어 외부 전송을 막던 제약이 사라졌습니다.

신호가 확실한 과제만 옮깁니다. 신호가 없는 과제까지 미리 옮기지 않습니다. 사내 환경을 갖추기로 했다면 그 일도 한 번에 전부 짓지 않고, 검증된 과제가 요구하는 만큼부터 갖춥니다.

## 6.5 이미 외부에서 돌리는 것을 되돌릴 것인가

퍼블릭 클라우드로 나간 작업을 사내로 되돌리는 것을 온프렘 회귀(repatriation)라고 부릅니다. 외부 조사들은 방향은 같되 폭은 다르게 보고합니다. Barclays의 CIO 설문에서는 다수의 CIO가 일부 작업을 되돌릴 계획이라고 답했지만, IDC 조사에서 전면 회귀를 계획한 곳은 소수에 그쳤습니다. 두 조사는 모수가 다르므로 나란히 비교할 수 없고, 수치와 한계는 [A1.2](../appendix/A1-appendix.md)에 적었습니다. 읽을 수 있는 것은 온프렘 회귀가 전면 철수가 아니라 선별적인 재배치로 나타난다는 점입니다.

판단할 때 살필 질문은 다음과 같습니다.

- **과금 방식이 무엇인가.** 쓴 만큼 내는 서비스는 그대로 두는 것이 기본입니다. 가동 여부와 무관하게 시간 단위로 비용을 내는 자원이 검토 대상입니다.
- **사용 양상이 예측 가능해졌는가.** 부하가 아직 출렁이면 사내의 고정비가 위험이 됩니다.
- **변동하는 작업과 꾸준한 작업을 가를 수 있는가.** 불규칙하게 몰리는 작업은 외부에, 꾸준히 도는 작업은 사내에 두는 혼합이 흔한 균형점입니다.
- **데이터가 강제하는가.** 데이터를 어느 관할에 두어야 하는지가 정해져 있다면 비용 계산보다 그 요건이 앞섭니다.
- **되돌리는 비용을 넣었는가.** 온프렘 회귀는 단순한 이전이 아닙니다. 데이터를 옮기는 비용, 새 장비에 드는 투자, 다시 구성하는 작업이 따르는 사실상의 새 구축입니다.

## 6.6 이 가이드가 다루지 않는 것

실행 환경의 구현, 제품 선택, 용량과 비용의 산정은 이 가이드의 범위 밖입니다. 사내 구축 경로의 한 예로 VMware Cloud Foundation 기반의 구성을 다루는 [VCF Private AI 가이드 시리즈](https://github.com/JaeHoYun/vcf-private-ai)가 있습니다. 다른 구현 경로를 택해도 이 장의 판단 축은 그대로 쓸 수 있습니다.
